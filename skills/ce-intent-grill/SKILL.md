# 问清需求

事实自己查图；决策问人。本步只出 markdown 草稿，不写正式计划，不写任何 CE yaml。问到「可以写命名计划」就停，不要开始改码，不要以 PR 为输入。

当前可问的决策一轮问完。每题带推荐答案。超时或中止前，已查到的结论仍须写进最终消息。

## 输入 / 输出 / 停

读：已记录意图、查图卡片。写：`staging.md`（或 `parts/*.md`）。不要写 `staging.yaml`。路径在当前 action 目录。

完成：未决要么已决，要么标了 UNRESOLVED 且带推荐答案。建议小节：范围、不做的事、测试内容、未决。

## 步骤

1. **先读已记录意图。** 用户已经说清的不要再问。用查图核对字段、路径、侧别（kernel / tiling / host / mixed），不要把命名相似当成同一符号。
2. **事实 vs 决策。** 图上能查到的（字段写读、是否已有同类实现、哪条 Host 路径）自己查。只有决策问人：范围边界、明确不做的事、Kernel vs Tiling 谁改、测试应覆盖什么。
3. **一轮问完当前可问的。** 每题带推荐答案（默认选哪条、为什么）。不要连环追问把对话拖成审讯。
4. **写入草稿小节。**
   - 范围
   - 不做的事
   - 测试内容（给 `/tg-plan` 读，不要编码成 CE yaml）
   - 未决决策（带推荐答案）
   - 侧别：kernel / tiling / host / mixed
5. **未决纪律。** 能决就决。不能决就 UNRESOLVED + 推荐答案，不要阻塞整个草稿。

## 常驻判断

`/ce-plan` 不以 PR / diff 为输入。贴 PR URL 是审查场景，不是本步。正式产物只有稍后的 `{slug}_plan.md`；本步不 promote 成 yaml，禁止 `tg_plan_intent.yaml`。

测试内容写给人与 `/tg-plan` 读的散文，不要在这里发明 `P-*` / `F-*` 表。场景 id 若出现，那是用户点名，不是本步推断矩阵。

LLM 禁止写 `.uo`。查图形态见 code-access 不变量。

## 看到这样

| 现象 | 判断 |

| 用户已经说清 | 不要再问 |
| 贴了 PR URL | 这是审查场景，不是本步 |
| 想写 yaml / 正式计划 | 禁止 |

## 循环

1. 读已记录意图。已说清的不再问。
2. 查图核对字段与侧别。事实不问人。
3. 把当前可问决策一次问完，每题带推荐答案。

## 输出形状

`staging.md` 小节固定为：范围、不做的事、测试内容、未决（带推荐答案）、侧别。不要 `staging.yaml`。测试内容给 `/tg-plan` 读，不要编码成 CE yaml。

## 反模式

- 图上能查的还问人
- 用户已说清的再问一遍
- 连环追问拖成审讯
- 以 PR 为输入
- 把测试内容写成 `P-*` 表或 CE yaml
- 未决既不决也不标 UNRESOLVED
