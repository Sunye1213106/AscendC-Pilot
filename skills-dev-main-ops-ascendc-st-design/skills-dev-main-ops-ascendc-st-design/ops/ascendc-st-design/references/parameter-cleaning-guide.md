# 参数功能说明内容清洗指南


## 1. 概述

算子资料中参数说明部分内容描述可能存在缺失、含糊或隐含约束未显式说明的问题。
参数清洗环节在输入文件校准阶段执行，对原始算子文档进行深度分析，生成清晰、
易懂、完备的参数说明文档（`01_parameter_description.md`），为后续参数定义和
约束分析提供可靠基础。

**常见问题**：①参数间约束描述含糊（如"shape需要是计算后的shape"缺少计算规则）；
②错误码中存在隐含约束（如"dtype和out不一致时报错"→dtype=out）；③功能说明信息
分散在多个章节需综合分析；④跨属性逻辑推断缺失（如dim元素不重复→length≤ndim）。

## 2. 清洗流程

清洗流程包含4个阶段：信息收集（§2.1）→ 综合分析与补全（§2.2~§2.10）→ 输出格式生成（§3）→ 矛盾处理（§4）。

### 2.1 信息收集

根据接口类型确定输入资料源，收集以下信息。

**接口类型与资料源对照**：

| 接口类型 | 主要资料源                                                   | 辅助资料源        |
| -------- | ------------------------------------------------------------ | ----------------- |
| aclnn    | `aclnn{Op}.md`                                               | `REQUIREMENTS.md` |
| REG_OP   | `{op}_op_host/{op}_def.cpp`（dtype/格式/默认值）<br>`{op}_op_graph/{op}_proto.h`（参数结构/约束关系）<br>`README.md`（功能说明/产品支持） | `REQUIREMENTS.md` |
| torchapi | `torch_npu-npu_{Op}.md`（op-plugin 接口文档，Python 签名）   | `REQUIREMENTS.md` |

#### 2.1.1 共同步骤（aclnn / REG_OP / torchapi 均需执行）

**S1. 产品支持确认与场景过滤**

1. **产品支持确认**：从 README.md（REG_OP）或 aclnn.md / torchapi.md 的"产品支持情况"章节获取目标产品支持列表。确认目标产品（默认 Ascend 950PR/950DT）是否在支持列表中；若不支持**立即中断流程**并汇总告知用户。

2. **场景子集提取**：从文档"功能说明"章节提取目标产品支持的场景子集（如"950PR 仅支持场景1-5"）。仅保留目标产品支持的场景，不支持场景从功能说明中删除。不支持场景独有的约束（如"场景七 num_head<4095"）不提取为 R{n}。

3. **dtype 产品隔离**：按 SKILL.md §1.3「产品隔离原则」处理 dtype 排除声明——仅目标产品自身的排除生效，其他产品的排除不影响。条件支持声明（如"仅场景1/2支持 FLOAT4"）：保留该 dtype，生成 R{n}。

4. **因子域影响记录**：在后续 A2/S2 提取参数属性时，对于维度、exist、枚举值等因子，标注其是否仅在目标产品不支持场景下可达（如"value 0维仅场景6可达，950PR 不支持场景6"）。此记录供步骤 2 YAML 映射时收窄因子域使用（见 test-factor-mapping-rules.md §4.1）。

**S2. 功能说明提取**

从 README.md（REG_OP）或 aclnn.md / torchapi.md 的"功能说明"章节提取算子的数学公式、计算逻辑和输入输出关系。

**S3. 参数约束关系提取**

从错误码章节（aclnn.md）、`{op}_proto.h` 的注释/宏定义结构（REG_OP）或"约束说明"章节（torchapi）中提取参数间的隐含约束关系。

#### 2.1.2 aclnn 专属步骤

**A1. 函数原型提取**

从 aclnn.md 提取 `aclnnStatus aclnn{Op}(...)` 和 `aclnnStatus aclnn{Op}GetWorkspaceSize(...)` 的函数原型，识别参数类型（aclTensor、aclIntArray、bool、aclDataType 等）和参数顺序。

**A2. GetWorkspaceSize 参数说明表提取**

从 aclnn.md 的参数说明表格中提取每个参数的描述、使用说明、数据类型、数据格式、维度、非连续 Tensor 支持等。

**A3. 返回值与错误码提取**

逐条分析 aclnn.md 错误码描述，提取参数间隐含约束。

#### 2.1.3 REG_OP 专属步骤

**R1. NPU 支持数据类型提取（`*_def.cpp`）**

从 `{op}_op_host/{op}_def.cpp` 的 `OpDef` 定义中提取各参数的 `.DataType({...})` 列表。这是**用例设计的 dtype 权威来源**。

**`ge::DT_*` 到标准 dtype 名称映射**：

| ge::DT_* 枚举   | 标准 dtype 名称 | ge::DT_* 枚举  | 标准 dtype 名称 |
| --------------- | --------------- | -------------- | --------------- |
| `DT_BF16`       | bfloat16        | `DT_FLOAT16`   | float16         |
| `DT_FLOAT`      | float32         | `DT_DOUBLE`    | float64         |
| `DT_INT8`       | int8            | `DT_INT16`     | int16           |
| `DT_INT32`      | int32           | `DT_INT64`     | int64           |
| `DT_UINT8`      | uint8           | `DT_UINT16`    | uint16          |
| `DT_UINT32`     | uint32          | `DT_UINT64`    | uint64          |
| `DT_BOOL`       | bool            | `DT_COMPLEX64` | complex64       |
| `DT_COMPLEX128` | complex128      |                |                 |

> **dtype 限制规则**：README.md 的参数说明表可能列出比 `*_def.cpp` 更多的理论 dtype（如 `NumberType()` 推导的全部类型）。用例设计**只覆盖 `*_def.cpp` 中 `.DataType({...})` 明确列出的 dtype**，其余 dtype 暂不考虑。
>
> 示例：AddN 的 README.md 列出 INT8, INT16, UINT8, DOUBLE, COMPLEX64 等 dtype，但 `add_n_def.cpp` 的 DataType 仅包含 `{DT_BF16, DT_FLOAT16, DT_FLOAT, DT_INT64, DT_INT32}`，则 01_parameter_description.md 的"数据类型"列只写 `bfloat16, float16, float32, int64, int32`。

**R2. 数据格式与 AI Core 配置提取（`*_def.cpp`）**

从 `*_def.cpp` 提取：

- `.Format({...})` → 参数支持的格式列表（如 `FORMAT_ND`）
- `.UnknownShapeFormat({...})` → 未知 shape 时的默认格式
- `OpAICoreConfig` 中的 `DynamicRankSupportFlag` / `DynamicShapeSupportFlag` → 动态维度/动态 shape 支持情况
- `.AddConfig("{产品型号}", ...)` → 产品支持列表（与 S1 交叉验证）

**R3. 参数默认值提取（`*_def.cpp`）**

从 `*_def.cpp` 的 `.Attr(...)` 定义中提取默认值：

- `.Int(default_val)` → 整型属性默认值
- `.Float(default_val)` → 浮点属性默认值
- `.Bool(default_val)` → 布尔属性默认值

默认值填入 01_parameter_description.md 的"取值范围"列注释中。

**R4. 参数结构提取（`*_proto.h`）**

从 `{op}_op_graph/{op}_proto.h` 的 `REG_OP` 定义块中提取参数结构：

- `.INPUT(name, TensorType)` → aclTensor，输入，必选
- `.DYNAMIC_INPUT(name, TensorType)` → aclTensorList，输入，必选
- `.OPTIONAL_INPUT(name, TensorType)` → aclTensor，输入，可选 (exist=[true,false])
- `.OUTPUT(name, TensorType)` → aclTensor，输出，必选
- `.REQUIRED_ATTR(name, Type)` → 对应标量类型，输入，必选
- `.ATTR(name, Type, default)` → 对应标量类型，输入，可选

**R5. TensorType 推导与 dtype 支持列表（`*_proto.h`）**

从 `TensorType({...})` 中的类型集合推导理论上支持的 dtype 范围（用于与 R1 的 `_def.cpp` DataType 交叉验证）：

| TensorType 成员    | 推导的 dtype 列表                                            |
| ------------------ | ------------------------------------------------------------ |
| `NumberType()`     | float16, float32, int8, int16, int32, int64, uint8, bfloat16 |
| `RealNumberType()` | float16, float32, int8, int16, int32, int64, uint8, bfloat16 |
| `DT_BOOL`          | bool                                                         |
| `DT_FLOAT`         | float32                                                      |
| `DT_FLOAT16`       | float16                                                      |
| `DT_INT32`         | int32                                                        |
| `DT_INT64`         | int64                                                        |
| `DT_UINT8`         | uint8                                                        |

> **交叉验证规则**：`_proto.h` 推导的 dtype 列表（理论范围）应**包含** `_def.cpp` 的 DataType 列表（实际范围）。若 `_def.cpp` 的 DataType 包含 `_proto.h` 推导范围之外的 dtype，标记为待确认项。

**R6. 参数间约束关系提取（`*_proto.h` + `*_def.cpp`）**

- 从 `*_proto.h` 的 `REG_OP` 宏结构提取参数间的输入/输出关系和必选/可选属性
- 从 `*_def.cpp` 的 `.ParamType()` 提取参数类型信息（DYNAMIC/REQUIRED/OPTIONAL）
- 参数顺序以 `*_def.cpp` 中 `.Input()` / `.Output()` / `.Attr()` 的声明顺序为准

#### 2.1.4 torchapi 专属步骤

torchapi 接口的详细清洗规则见 [torchapi-cleaning-guide.md](torchapi-cleaning-guide.md)。本节给出摘要步骤：

**T1. Python 函数原型解析**
从 `torch_npu.npu_{Op}(...)` 签名提取参数顺序、`*` kwargs 分隔符、`=默认值`（判定必选/可选）、`-> Tensor` 返回值。详细解析规则见 torchapi-cleaning-guide §2.2。

**T2. Bullet-list 参数说明解析**
逐 bullet 结构化拆解（参数名/Python 类型/必选可选/dtype/format/shape/取值范围/非连续）。拆解模式表见 torchapi-cleaning-guide §2.3。

**T3. torchapi 参数类型映射**

| torchapi 原始类型 | 清洗后"类型"列 |
|-------------------|---------------|
| `Tensor`（必选） | `aclTensor` |
| `Optional[Tensor]` / `Tensor=None` | `aclTensor`（"必选/可选"列填"可选"） |
| `List[int]` | `aclIntArray` |
| `List[float]` | `aclFloatArray` |
| `int` | `int64_t` |
| `float` | `float` |
| `bool` | `bool` |

完整映射表（含 List[bool]/str/torch.dtype/返回值等）见 torchapi-cleaning-guide §4。

**T4. 返回值说明解析**
`-> Tensor` 作为输出参数处理（参数名通常为 `out`）；返回值说明中的条件分支（如"当 scale 有值时 dtype 仅为 int8"）提取为约束关系 R{n}。详见 torchapi-cleaning-guide §2.5。

**T5. 预留参数处理**
文档标注"当前版本暂不支持该参数"的参数，exist=[false]，不生成 required_param_missing 异常，改生成 reserved_param_used 异常。详见 torchapi-cleaning-guide §5。

> **核心差异**：torchapi 无错误码表，本指南 §2.3 错误码隐含约束挖掘策略不适用。隐含约束使用 torchapi-cleaning-guide §3 的替代策略（默认值推断 + 功能说明反推 + 参数描述值域提取 + 返回值条件分支）。

### 2.2 功能说明推断

根据算子的功能描述，推断输出shape的计算方式。以reduce类算子为例：

**功能说明**：将tensor中NaN处理为0后，返回输入tensor给定维度上的和。

**推断规则**：
- 输入self的shape为 `[d0, d1, ..., dn]`
- dim指定要缩减的维度，keepDim指定是否保留缩减维度
- 当keepDim=true时，out.shape中dim指定的维度值为1，其余与self.shape相同
- 当keepDim=false时，out.shape中不包含dim指定的维度

### 2.3 错误码隐含约束

逐条分析错误码描述，提取参数间的隐含约束关系。**重点关注**：错误码中可能包含参数说明表未提及的约束（如参数表仅写"取值范围"而未提唯一性，但错误码中有"dim指定的轴重复"）。务必逐条将错误码与参数说明表交叉比对，提取遗漏的约束。

| 错误码描述 | 推断出的约束 |
|------------|-------------|
| dtype和out的数据类型不一致时 | dtype的数据类型必须与out的数据类型一致 |
| self或out的数据类型不在支持范围内 | self.dtype和out.dtype必须同时取自支持列表 |
| dim数组中的维度超出输入tensor的维度范围 | dim中每个元素值必须在[-self.dim(), self.dim())范围内 |
| dim指定的轴重复 | dim中各元素值不允许重复 |
| self或out的shape超过8维 | self和out的维度数最大为8 |
| out shape与实际不匹配 | out.shape必须等于根据self.shape、dim、keepDim计算得出的实际输出shape |

### 2.4 dtype 约束语义解析

在完成功能说明推断（§2.2）和错误码提取（§2.3）后，对涉及参数间**数据类型约束关系**的描述进行语义解析。本步骤处理的输入包括：参数说明表的"使用说明"列、§2.3 从错误码提取的 dtype 约束。

**核心问题**：参数说明中描述 dtype 约束的措辞多样（"一致"/"推导规则"/"可转换"/"对应"等），仅凭关键词匹配无法准确判定约束的运算语义。必须通过理解约束描述的**运算语义**来确定约束类型，并通过引用文档和源码进行验证。

#### 2.4.1 约束类型判定

对每条涉及"数据类型"的约束描述，按以下优先级顺序匹配**首个命中**的关键词模式，确定约束类型：

| 优先级 | 文本关键词模式 | 约束类型 | 子类型 | 说明 |
|--------|--------------|---------|--------|------|
| 1 | "相等"/"相同"/"一致"/"保持一致"（**排除**"推导之后的...一致"） | **等值** | — | 两个参数dtype必须**完全相同** |
| 2 | "推导之后的...一致"/"推导后...保持一致" | **推导** | `[推导后一致]` | "一致"修饰的是**推导结果**而非输入参数 |
| 3 | "推导后可转换"/"推导后...转换"/"可转换为...推导后的" | **推导** | `[推导后转换]` | 先推导再转换。**必须按下方方向消歧规则确定转换方向** |
| 4 | "可转换"/"可转化" | **转换** | — | 一个dtype变为另一个dtype。**必须按下方方向消歧规则确定转换方向** |
| 5 | "推导规则"/"互推导"/"满足...推导"/"满足数据类型推导规则" | **推导** | `[互推导]` | 允许不同dtype，只要求PromoteType有效。**不要求相同** |
| 6 | "对应"/"需满足"（未说明具体运算关系） | **歧义** | → §2.4.2 | 含义不明，需证据求解 |

**转换方向消歧规则**（命中优先级 3 或 4 时必须执行）：

`can_convert_dtype(source, target)` 有严格的方向性。约束文本"A 可转换为 B"中，A = source（第一个参数），B = target（第二个参数）。但自然语言的主动宾关系常有歧义，**必须通过以下流程确定方向**：

**步骤 1：识别文本中的两个角色**

| 角色标记 | 含义 | 识别方法 |
|---------|------|---------|
| 被约束参数 | 约束描述的对象（通常是输出参数或被 @solves 求解的参数） | 看约束所在的参数行（如 out 的"补充说明"列） |
| 推导结果 | PromoteType 运算的返回值 | 文本中的"推导后的数据类型"/"推导结果"/"PromoteType结果" |

**步骤 2：确定方向**

| 约束文本中的措辞 | source | target | `can_convert_dtype` 调用 |
|-----------------|--------|--------|--------------------------|
| "被约束参数 可转换为 推导结果" | 被约束参数 | 推导结果 | `can_convert_dtype(被约束参数, 推导结果)` |
| "推导结果 可转换为 被约束参数" | 推导结果 | 被约束参数 | `can_convert_dtype(推导结果, 被约束参数)` |

**步骤 3：歧义文本的处理**

当文本主宾关系不明确时（如"数据类型需要是X可转换的类型"——"数据类型"是 source 还是 target？），**必须通过证据确认方向**：

| 证据来源 | 操作 | 示例 |
|---------|------|------|
| **错误码措辞**（优先级最高） | "推导出的数据类型无法转换为指定输出out的类型" → source=推导结果, target=out | aclnnCat |
| **源码 Cast 调用** | `Cast(infer_result, out_dtype)` → source=推导结果, target=out | — |
| **语义推理** | 算子计算结果类型为推导结果，需要 Cast 到用户指定的 out 类型 → source=推导结果, target=out | 大多数算子 |
| **无法确定** | 标注"（方向歧义，待人工确认）"，在追溯表中标记 `[方向歧义]` | — |

**歧义案例**：

| 原文 | 表面理解 | 正确方向（由错误码确认） | 说明 |
|------|---------|----------------------|------|
| "数据类型需可转换为 tensors 内部推导后的数据类型"（aclnnCat out 参数） | out → promote_result | promote_result → out | "需可转换"的主语是"数据类型"(out)，但错误码"推导出的数据类型无法转换为指定输出out的类型"明确方向是 promote_result→out |

> **关键原则**：当约束文本的主宾关系有歧义时，**永远优先使用错误码措辞确认方向**。错误码通常更精确地描述了"谁转谁"的关系。无错误码时，按"推导结果是计算的实际类型，需 Cast 到用户指定的输出类型"的通用规则理解。

**基本概念**：
- **等值**：`dtype_A == dtype_B`，两个参数的 dtype 必须完全相同
- **推导**(PromoteType)：两个 dtype 作为输入产生结果 dtype
  - Tensor+Tensor：参见 `互推导关系.md`（18×18 查找表）
  - Tensor+Scalar：参见 `TensorScalar互推导关系.md`（16×16 查找表，与TT有13处差异）
- **转换**(Cast)：一个 dtype 变为另一个 dtype
  - Tensor+Tensor：参见 `互转换关系.md`（4 条规则）
  - Tensor+Scalar：参见 `ConvertToTensor.md`（接口7，23 种类型全连接矩阵）

> "转换为FLOAT16计算"等内部行为描述不是参数间约束。约束中涉及aclScalar参数时，
> 推导和转换使用不同的查找表和工具函数，详见 constraint-writing-guide.md 模式1.5/2。

#### 2.4.2 歧义处理与证据验证

当 §2.4.1 速查表命中优先级 6（"对应"/"需满足"等歧义措辞），或文本语义本身含糊，或命中优先级 3/4 但转换方向不明确时，按以下优先级寻找证据消除歧义，**找到即停止**：

| 优先级 | 证据来源 | 操作 |
|--------|---------|------|
| 1 | **源码** | 搜索 `OP_CHECK_DTYPE_NOT_MATCH`(→等值) / `PromoteType`(→推导) / `Cast`(→转换) / `ConvertToTensor`(→TS转换)。源码优先级高于文档 |
| 2 | **引用文档的查找表** | 如果有 `互推导关系.md` 链接，按推导约束处理 |
| 3 | **算子自身的映射表** | 如果约束说明中有 dtype 映射表（§2.9 识别的结构化约束数据），按映射表处理 |
| 4 | **最宽松默认** | 以上都无结果 → 不限制参数间的 dtype 关系，在"补充说明"中标注"（约束描述歧义，未限定参数间 dtype 关系，待人工确认）" |

"最宽松默认"意味着：不限制参数间的 dtype 关系（允许任意组合），但仍限制每个参数自身的 dtype 支持列表（来自"数据类型"列）。

> **追溯表标记**：按"最宽松默认"处理的 R{n}，在 `04_constraints.py` 追溯表中应标记为 `[歧义-最宽松]`（如 `R{n} ({描述}) → solve_{target}_dtype [歧义-最宽松] → Candidates`），以便在后续步骤中快速定位需要人工确认的约束。此标记同时触发 `--validate` 输出 `[AMBIGUOUS-DTYPE]` 告警，提醒审查。

**证据链验证**：语义判断完成后，必须通过证据链验证初步分类的正确性：

| 验证级别 | 操作 |
|---------|------|
| **引用文档** | 检查超链接：`互推导关系.md`(推导) / `TensorScalar互推导关系.md`(TS推导) / `互转换关系.md`(转换) / `ConvertToTensor.md`(接口7转换)。链接与文本矛盾时以文本为准（ConvertToTensor.md链接例外：以链接为准） |
| **源码** | 搜索`OP_CHECK_DTYPE_NOT_MATCH`(→等值) / `PromoteType`(→推导) / `Cast`(→转换) / `ConvertToTensor`(→TS转换)。源码优先级高于文档 |
| **产品限制** | 按 §2.1.1 S1 产品隔离原则，仅扣除目标产品自身的显式排除规则。其他产品的排除不影响 |

源码优先级高于文档描述。本步骤是 §2.8 交叉验证与矛盾检测在 dtype 维度的特化，矛盾按 §4 流程中断并汇总。

#### 2.4.3 写入格式与N值计算

将验证通过的约束写入"补充说明"列，格式如下：

| 约束类型 | "补充说明"列格式 | 适用场景 |
|----------|-----------------|---------|
| 等值 | `数据类型需与{param}一致` | 参数间 dtype 必须完全相同 |
| 推导 `[互推导]` | `数据类型与{param1}与{param2}满足推导规则（参见互推导关系.md），合法组合：{N}种` | 两个参数间 PromoteType 有效即可 |
| 推导 `[推导后一致]` | `数据类型需等于{param1}与{param2}推导后的数据类型（参见互推导关系.md），合法组合：{N}种` | 输出等于推导结果 |
| 推导 `[推导后转换]` | `数据类型需可转换为{param1}与{param2}推导后的数据类型（参见互推导关系.md和互转换关系.md），合法组合：{N}种` | 先推导再转换 |
| 转换 | `数据类型需可转换为{param}（参见互转换关系.md）` | 一个 dtype 可转换为目标 |
| ConvertToTensor 转换 | `数据类型满足ConvertToTensor接口7转换规则（参见ConvertToTensor.md），合法组合：{N}种` | 链接指向 ConvertToTensor.md |
| 歧义（最宽松默认） | `（约束描述歧义，未限定参数间 dtype 关系，待人工确认）` | 无法判定 |
| TensorList 内部 `[互推导]` | `列表内部各 tensor 的 dtype 须满足互推导规则（参见互推导关系.md），合法两两推导对：{N}种；本约束将触发 dtype_list 因子生成（见步骤2/3）` | aclTensorList 内部元素间 |

**"数据类型"列**：列出该参数支持的所有 dtype，**不因约束关系而缩减**。约束关系仅在"补充说明"列体现。

**TensorList "数据类型"列附加文本**：

| 约束类型 | 附加文本 |
|----------|---------|
| `[互推导]` 内部 | `；列表元素间 dtype 可不同（须满足补充说明中的推导规则）` |
| 等值 内部 | `；列表元素间 dtype 必须相同` |
| 无内部约束 | 不附加 |

**N 值统一计算方法**：

```
N = |{组合 ∈ D₁×...×Dₖ : 全部 pairwise 推导有效}|
（k=2退化为两参数公式；TensorList内部约束：D₁和D₂均为该参数的dtype支持列表，因约束两端都是同一列表的内部元素）
计算：①查互推导关系.md查找表 → ②扣除产品特定排除 → ③剩余数=N
```

> "推导后一致"和"推导后转换"的 N 值含义是**推导源的合法组合数**，而非目标参数候选数（目标值由推导结果唯一确定）。

### 2.5 内存复用参数识别

部分算子存在内存复用（地址复用/in-place）参数——同一个 tensor 既是输入（提供初始数据）又是输出（写入结果）。在参数清洗阶段识别此类参数，并在"补充说明"列标注。

**识别信号**：

| 信号层级 | 信号来源 | 判定规则 | 可靠性 | 可用性 |
|---------|---------|---------|--------|--------|
| **主信号** | 接口文档参数表 | "输入/输出"列值为"输入/输出" | 强 | agent 可直接获取 |
| **辅助信号** | 函数原型 | aclTensor 指针参数无 `const` 修饰，且语义为"更新/修改" | 中（纯输出参数也无 const，不具区分性） | agent 可直接获取 |
| **确认信号** | 算子 proto 定义 | 同一参数名同时出现在 `.INPUT(...)` 和 `.OUTPUT(...)` 中 | 强 | agent 通常无法访问源码，仅供人工确认 |

**判定规则**：以主信号（文档"输入/输出"列 = "输入/输出"）为唯一充分条件。辅助信号（无 const）仅供交叉验证，不作为独立判定依据。

**"补充说明"列标注格式**：

```
内存复用参数（推断自：文档'输入/输出'列标注为'输入/输出'）
```

**"输入/输出"列处理**：保持原文"输入/输出"不变，不做二值简化。

### 2.6 跨属性逻辑推断

在完成功能说明推断（§2.2）和错误码提取（§2.3）后，对所有参数系统性地检查以下推断模式，将推导结论写入对应参数的"维度/长度"或"补充说明"列，并标注 `（推断自：...）`。

**推断模式清单**：

| # | 模式 | 触发条件 | 推断结论 | 典型场景 |
|---|------|----------|----------|----------|
| 1 | 唯一性→长度上界 | Array元素"不允许重复/不能相同"，取值范围依赖另一参数 | length ≤ 有效唯一值数 | reduce类算子的dim：元素不重复且范围[-N,N) → length ≤ N |
| 2 | 负索引等价 | 整数范围包含负索引（如[-N, N)），语义上-i等价于N-i | 有效唯一值数为N而非2N | dim=[0, -4]对4D tensor视为重复 |
| 3 | 耦合长度传播 | 多个Array声明"长度相同/一致" | 任一Array的长度约束传播到所有耦合Array | SliceV2的starts/ends/axes/steps |
| 4 | 条件化绑定 | bool/enum参数决定Array长度与谁匹配 | 用条件约束表达 | ConfusionTranspose的transposeFirst |
| 5 | 求和→长度上界 | sum(Array)==某值且每个元素≥1 | length ≤ 该值 | SplitWithSize的splitSizes |
| 6 | **存在性推断** | 指针类型参数（aclTensor*、aclScalar*、aclIntArray* 等），且具备可选信号（参数名含 Optional / NULLPTR 错误码未列出 / 文档明确说明） | 判定为可选参数，填写 exist=[true,false] | addr 的 betaOptional、stft 的 windowOptional、sinkhorn 的 tol |
| 7 | **条件化属性传递** | 参数 B 的文档描述中出现"由参数 A（的某个属性）控制/决定/影响"参数 B 的某属性。控制源 A 可以是：bool 标量值、enum 值、Array 某元素值、另一个参数的 null 状态。被控属性可以是：exist、shape、dtype、value 约束。 | 参数 B 的被控属性不是静态值，而应由 @solves 从参数 A 推导。在"必选/可选"列标记为"条件可选"或在"补充说明"中明确控制关系，并在约束关系章节新增 R{n}。 | LayerNormBackward 的 gradInputOut 由 outputMask[0] 控制 exist；UniqueConsecutive 的 inverseOut 由 returnInverse 控制 exist |
| 8 | **语义值域推断** | "取值范围"列内容为自然语言功能描述（不含显式值域符号 ≥、≤、∈、[]、()等），但描述中的业务语义隐含了值域约束 | 将隐含值域约束重写到"取值范围"列，格式：`{原文}；推断值域：{显式值域}（推断自：{语义依据}）`。若参数为非 Tensor 类型（aclIntArray / aclFloatArray / aclScalar / int64_t / float 等），同时按 §3.3 格式在 `## 约束关系` 章节追加 R{n} 条目（标题：`R{n}: {参数名}推断值域约束`），确保该约束进入后续追溯体系。Tensor 类参数的值域通过步骤 2 的 value_range_{dtype} 处理，无需生成 R{n}。 | 见下方语义关键词表 |

> **模式 #7 与模式 #4 的关系**：模式 4（条件化绑定）处理"bool/enum 决定 Array 长度与谁匹配"，是属性传递在 Array 长度维度的特化。当控制目标涉及 exist、dtype、value 等非长度属性，或控制源为 BoolArray 元素 / null 状态等非 bool/enum 类型时，应按模式 #7 处理。当两者均可适用时，优先按模式 #7（属性传递语义更通用）。模式 #7 的触发信号识别详见 [constraint-writing-guide.md](constraint-writing-guide.md) 模式 7 情况 E 的识别信号速查表。

**模式 #8 语义关键词识别规则**：

对每个参数的"取值范围"列执行以下检查：

1. 若该列已包含显式值域符号（≥、≤、>、<、∈、[]、()、[lo,hi] 等）→ **跳过**（已有显式约束）
2. 若该列为 `-`、`不适用` 或 `不适用（输出参数）` → **跳过**（无值域）
3. 若该列内容为自然语言描述 → 扫描以下语义关键词：

| 语义类别 | 关键词示例 | 隐含值域 | 推断依据模板 |
|---------|-----------|---------|------------|
| 计数/数量 | token数、个数、数量、计数、长度、size | ≥0 | 语义为计数，计数不可能为负 |
| 索引/位置（非负语境） | 索引、位置、偏移、下标（当文档中索引范围不含负值时） | ≥0 | 语义为非负索引 |
| 概率/权重（归一化） | 概率、权重、系数（归一化语境） | [0,1] 或 ≥0 | 语义为概率/权重系数 |
| 比例/比率 | 比例、比率、rate | >0 或 ≥0 | 语义为比率 |

4. **仅当语义关键词明确排除某些值时才推断**。若描述不含上述关键词或关键词不排除任何值（如"调优参数"、"预留参数"），**不推断**，保持原文不变
5. 推断结论重写到"取值范围"列，格式：`{原文}；推断值域：{显式值域}（推断自：{语义依据}）`

**执行要点**：
1. **逐参数扫描**：对每个 Array/ScalarList 参数，检查其取值范围和补充说明是否包含唯一性约束
2. **组合推导**：若存在唯一性约束，分析有效唯一值数量（注意负索引等价），推导长度上界
3. **传播检查**：若多个 Array 存在长度耦合，检查长度上界是否传播
4. **标注来源**：所有推导结论必须标注推断依据，如 `（推断自：元素不重复 + 范围[-N,N)）`
5. **语义值域扫描**：对所有参数的"取值范围"列按模式 #8 执行语义关键词扫描，将命中的隐含值域重写为显式值域
5b. **推断值域 R{n} 结构化输出**：若步骤 5 中为某个非 Tensor 参数生成了"推断值域"标注，则同时在该参数对应的 `## 约束关系` 章节追加 R{n} 条目：
```
### R{n}: {参数名}推断值域约束
涉及参数: {参数名}.value
条件因子: {无}（或标注值域依赖的其他参数）
来源: 参数说明表"取值范围"列（推断自：{语义依据}）
{原文描述}。推断值域：{显式值域表达式}
```

### 2.7 可选参数识别

对所有**指针类型参数**（aclTensor*、aclScalar*、aclIntArray*、aclFloatArray*、aclBoolArray*、aclScalarList*、char* 等），系统性地检查以下信号，判定其是否为可选参数。值类型参数（bool、int64_t、aclDataType 等）天然不可为 null，直接判定为必选。

> **char*/enum 选择器例外**：若该可选指针参数是"选择器语义"（其取值触发算子不同执行路径，如 `cacheMode`/`scatterMode`/`reduceMode`），且文档/约束存在"某场景下必须取特定非默认值"的要求，则在"必选/可选"列标记为**"条件可选"**，**不要**把 `exist` 写死为 `[true,false]`，改交由 `04_constraints.py` 的 `@solves` 从控制因子推导（见 [constraint-writing-guide.md](constraint-writing-guide.md) §4.4 "反模式：选择器参数 .exist 解耦"）。否则清洗阶段会持续种下自由锚点，导致约束阶段漏 override。

**判定流程**：

```
对每个指针类型参数 P:
  1. 若 P 是值类型（bool、int64_t、aclDataType 等非指针类型。注意 char* 是指针类型，不在此列） → 必选（结束）
  2. 若文档在"使用说明"、"描述"或"取值范围"列明确写明 P "传入空指针"、"为空时"、"可选输入"等文本，或取值范围中出现"空指针"与枚举值并列（如"'XXX'或空指针"、"空指针或'YYY'"）:
     → 判定为可选（结束）
     → 在"必选/可选"列填写: "可选（推断自：文档明确说明'...')"
     → 注意：取值范围中的"空指针"表示 exist=False，不应作为 value 的枚举值
  3. 若文档写明"预留参数，入参请用空指针代替":
     → 判定为必须为nullptr（结束）
     → 在"必选/可选"列填写: "必须为nullptr（推断自：文档写明'预留参数'）"
  4. 若仅参数名含 "Optional" 后缀:
     → 倾向可选但需注意（结束）
     → 在"必选/可选"列填写: "可选（推断自：参数名含Optional后缀）"
     → 在"补充说明"列标注: "注意：仅单一信号支持，需组合多信号交叉验证，单一Optional后缀不可靠"
  5. 以上均未命中 → 默认判定为必选；然后检查条件化属性传递信号：
     a. 扫描参数的"补充说明"和错误码，查找以下核心信号措辞：
        - "由XX[N]控制是否输出" / "由XX控制是否输出" → 被控属性为 exist
        - "当XX为True时有意义" / "当XX为True时有效" → 被控属性为 exist
        - "当XX为True时必须非空" / 错误码"XX为True且P为空指针" → 被控属性为 exist
        - "仅当XX不为空时生效" / "XX为空时无效/不处理" → 被控属性为 exist 或 value 约束
        - "当XX为True/False时，shape为..." → 被控属性为 shape
        - "当XX为True/False时，数据类型为..." → 被控属性为 dtype
        - "当XX为某值时，该参数的值不能为..." → 被控属性为 value 约束
        - "XX为空时，shape为A；XX不为空时，shape为B" → 被控属性为 shape
     b. 若命中任何信号：
        → **覆盖**步骤 5 的"必选"判定，在"必选/可选"列标记为"条件可选（推断自：由XX控制是否输出）"
        → 在"约束关系"章节新增 R{n}: "{控制参数}.{属性} → {本参数}.{被控属性}"
        → 标记本参数的被控因子不由 YAML 静态定义，而由 @solves 推导
     c. 识别范围不限于 BoolArray（outputMask）：bool 标量（returnInverse）、enum（fusedOpType）、null 状态（scales2Optional 为空）都可以作为控制源
```

**推断依据标注格式**：

在"必选/可选"列和"补充说明"列中标注推断依据：
- `可选（推断自：参数名含Optional后缀）`
- `可选（推断自：文档明确说明'如果传入空指针，则取默认值'）`
- `必须为nullptr（推断自：文档写明'预留参数，入参请用空指针代替'）`

**默认值处理**：若文档未写明可选参数的默认值，在补充说明中标注"默认值未知（文档未说明）"，不依赖源码推断。

### 2.8 交叉验证与矛盾检测

将各信息源提取的约束进行交叉比对：
- 若同一参数在不同章节的描述存在矛盾，标记为待确认项
- 若约束关系无法从现有信息推断得出，标记为待确认项
- 若参数类型从函数原型推断的结果与参数说明表不一致，标记为待确认项

### 2.9 结构化约束数据识别

在完成步骤 2.2~2.8 后，对全信息源执行跨参数约束扫描。**本步骤无条件执行**，
不依赖任何触发信号。

依次检查约束说明章节、错误码章节、参数说明表、功能说明，识别涉及两个或以上
参数的结构化约束数据（映射表、公式、排除列表、条件化规则等）。

**保留规则**：

1. **原格式保留**：映射表保持表格、公式保持公式。不做任何压缩或改写
2. **标注涉及参数**：区分以下角色：
   - **被约束参数**：值域/属性被限制的参数
   - **条件因子**：约束生效的前提条件参数（如场景变量、枚举参数）
   - **推导目标**：值由约束计算得出的参数
   格式：`被约束: {param.attr}; 条件: {param.attr}; → {target.attr}`
   无条件约束时"条件"项省略
3. **标注来源**：注明数据来自文档的哪个章节
4. **无发现则跳过**：若未发现结构化约束数据，本步骤结束

**场景→属性映射约束**：当文档中同一参数在不同场景（如场景一/二/四/五）下有不同属性值（如 shape 公式不同、dtype 不同），应将场景→属性映射作为独立 R{n} 提取。此类约束本质上是"场景参数 → 目标参数属性"的跨参数约束：场景变量 `_scenario.value` 为条件因子，被约束参数为目标属性。R{n} 中应列出每个场景对应的属性公式或取值。

#### 2.9.1 InfNan 支持声明识别

扫描文档"约束说明"章节，识别以下措辞模式：

| 文档措辞 | 判定结果 | YAML 标注 |
|---------|---------|----------|
| "不支持inf/nan" / "不支持±inf和nan" / "输入不支持有inf和nan" / "不支持有±inf和nan的情况" | 不支持 | `support_infnan: false` |
| 无相关措辞 | 默认支持 | 不标注（默认 `true`） |

1. 在参数列表表格的"补充说明"列标注"不支持inf/nan（来源：约束说明章节）"
2. 在 Step 2 YAML 中对所有含 float dtype 的输入 tensor 设置 `support_infnan: false`（与 `type`/`io_type` 同级，不在 `factors` 下）
3. 输出参数不受此约束影响（输出值由算子计算逻辑决定）

#### 2.9.2 空 tensor 支持声明识别

**识别规则**：01 参数表"空tensor"列标注为"不支持"的 Tensor/TensorList 参数，

- QA Q7b（ET 完备性增强）跳过该参数的零轴覆盖检查
- 生成器跳过该参数的 ET 场景目标生成
- 生成器为该参数生成 L2 异常用例（shape=[0,...]），验证算子正确拒绝空输入

### 2.10 部分约束补集处理

当文档约束仅覆盖参数空间的子集时（如"涉及类型A、B的，只支持如下路径"），需对文档未描述的补集空间执行以下规则：

1. **禁止自行编造补集规则**：文档未描述的转换路径，不得以通用类型推导规则（如"整数间可互转、浮点间可互转"）填充。应标注为"文档未约束"并进入规则2
2. **间接证据交叉验证**：扫描文档全信息源（约束说明、错误码、功能说明），收集补集空间的间接证据。间接证据类型：
   - **行为描述**：如"浮点→整型时 NaN 转0"→ float→int 路径合法
   - **精度限制描述**：如"int32→int8 精度有限"→ int32→int8 路径合法
   - 合并间接证据推断补集规则，写入约束关系章节
3. **推断标注必须**：补集空间的推断结论须标注来源，格式：`（推断自：间接证据A + 间接证据B）` 或 `（推断自：文档未约束，按算子语义推断为任意类型间可互相转换）`

### 3.4 约束提取反向校验

对 01_parameter_description.md 中"取值范围"列和"补充说明"列的每个约束表达式，执行以下校验：

1. **定位原文**：在原始文档中找到对应参数的约束文本
2. **逐条比对**：将参数描述表中的约束表达式与原文比对
3. **标记状态**：
   - `EXACT_MATCH`：原文有精确对应
   - `INFERENCE`：从原文推断，已标注推断依据
   - `MISMATCH`：与原文不一致，需修正
   - `NEW`：参数描述表中存在但原文中找不到对应
4. **符号化映射表**（强制）：以下原文表述**必须**映射为对应的符号化结果：

| 原文表述 | 符号化结果 |
|---------|-----------|
| "大于0" / ">0" / "应大于0" / "必须大于0" / "应为正数" | `> 0` |
| "大于等于0" / "≥0" / "不小于0" / "非负" | `≥ 0` |
| "小于0" / "<0" | `< 0` |
| "不重复" / "不能重复" / "保证不重复" | `不重复` |
| "长度为N" / "数组长度为N" | `长度=N` |

若符号化结果在映射表中对应的原文模式集合不包含实际原文，则标记为 MISMATCH。

5. **产出要求**（强制）：将所有约束项的校验结果汇总为反向校验表，追加到 `01_parameter_description.md` 末尾。格式如下：

```markdown
## 约束提取反向校验表

| R{n} | 约束项 | 原文片段 | 符号化 | 转录结果 | 状态 |
|------|--------|---------|--------|---------|------|
| R13 | stridesOptional取值 | "其值应该大于0" | > 0 | 每个元素>0 | EXACT_MATCH |
| R14 | compressLens值域 | — | — | 每个元素≥0（推断自：语义为压缩量） | INFERENCE |
```

字段说明：
- `原文片段`：从原始文档复制的约束文本，用引号包裹；无直接对应时填"—"
- `符号化`：按映射表转为标准符号；无直接对应时填"—"
- `转录结果`：参数描述表中的实际内容
- `状态`：EXACT_MATCH / INFERENCE / MISMATCH / NEW

**任何 MISMATCH 项必须立即修正参数描述表后再继续后续步骤。步骤 4A `--validate` 会程序化检查此表，存在 MISMATCH 项时阻断流程。**

## 4. 矛盾处理

若在清洗过程中发现以下情况，**立即中断流程**并汇总告知用户需要确认的内容：

1. **参数描述矛盾**：同一参数在不同信息源中有相互矛盾的描述
2. **约束无法推断**：参数间的约束关系无法从现有信息中推导得出
3. **功能说明不充分**：无法根据功能说明推断出输出参数的计算规则
4. **数据类型不一致**：函数原型、参数说明表、错误码中提及的数据类型列表不一致
